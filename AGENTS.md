## Skill Loading

Before editing files for a substantial task:
- Run `pnpm dlx @tanstack/intent@latest list` from the workspace root to see available local skills.
- If a listed skill matches the task, run `pnpm dlx @tanstack/intent@latest load <package>#<skill>` before changing files.
- Use the loaded `SKILL.md` guidance while making the change.
- Monorepos: when working across packages, run the skill check from the workspace root and prefer the local skill for the package being changed.
- Multiple matches: prefer the most specific local skill for the package or concern you are changing; load additional skills only when the task spans multiple packages or concerns.

# Project Context

## Provenance

Scaffolded with the TanStack CLI:

```bash
npx @tanstack/cli@latest create my-tanstack-app --agent --package-manager pnpm --tailwind --add-ons tanstack-query,convex,shadcn
```

- Framework: React, TanStack Start (file-based routing), Vite
- `--tailwind` is currently a no-op flag on this CLI version — Tailwind v4 is enabled by default in the standard TanStack Start scaffold.
- The project files were generated into a nested `my-tanstack-app/` folder by the CLI (it always creates its own directory) and then moved up into the repo root so the repo root *is* the app root.

Follow-up commands run after scaffolding:

```bash
npx @tanstack/intent@latest install   # wires skill-loading guidance into AGENTS.md
npx @tanstack/intent@latest list      # lists all intent-enabled packages/skills available locally
```

`intent install` regenerates the "Skill Loading" block at the top of this file — if you edit that block, keep it intact or reinstall will conflict with your edits.

Added manually after scaffolding (see "Deployment" below):

```bash
pnpm add nitro@npm:nitro-nightly@latest
```

## Environment variables

Defined in `.env.example` (copy to `.env.local`, which is gitignored):

| Variable | Required | Purpose |
|---|---|---|
| `CONVEX_DEPLOYMENT` | for `convex dev`/`convex deploy` tooling | Identifies which Convex deployment the CLI talks to |
| `VITE_CONVEX_URL` | yes, at runtime | Convex deployment URL the client (`src/integrations/convex/provider.tsx`) connects to. Missing value logs a console error and the app will fail to reach Convex. |

Setup: `pnpm dev` (see "Dev workflow" below) runs `convex dev` for you, which on first run logs in, creates/links a Convex project+deployment, and writes `CONVEX_DEPLOYMENT`/`VITE_CONVEX_URL` into `.env.local`.

This repo is already linked to a real Convex deployment:
- Team: `walter-furrer`, Project: `bullshit-corner`
- Dev deployment: `dev:avid-stoat-60` (dashboard: https://dashboard.convex.dev/t/walter-furrer/bullshit-corner)

For Vercel: add `CONVEX_DEPLOYMENT` and `VITE_CONVEX_URL` as Vercel project environment variables (Production/Preview/Development as appropriate) — typically pointed at a **prod** Convex deployment for the Vercel Production environment, and `npx convex deploy` should be run (e.g. in CI or manually) whenever `convex/` changes, since Vercel only builds the frontend and does not push Convex functions itself.

## Dev workflow

`pnpm dev` runs the Vite dev server and `convex dev` together via `concurrently` (output prefixed `[web]` / `[convex]`, ports/colors as configured in `package.json`):

```json
"dev": "concurrently -n web,convex -c blue,magenta \"pnpm dev:web\" \"pnpm dev:convex\"",
"dev:web": "vite dev --port 3000",
"dev:convex": "convex dev"
```

Run them separately (`pnpm dev:web`, `pnpm dev:convex`) if you need isolated logs, e.g. while debugging one side.

Gotcha: `convex dev` needs an authenticated CLI and a linked project. In an already-authenticated environment with no linked deployment yet, it can silently auto-create a new Convex project on first run instead of prompting — this happened once while verifying this setup (see git history / team dashboard for the `bullshit-corner` project it created). In a fresh/unauthenticated environment it will instead prompt interactively for login, so the very first `pnpm dev` there may need a real terminal (not a CI job) to complete that flow.

## Deployment (Vercel)

TanStack Start deploys via Vite + Nitro (per the `@tanstack/start-client-core#start-core/deployment` Intent skill — see below). The base scaffold doesn't ship a server preset, so Nitro was added explicitly:

```bash
pnpm add nitro@npm:nitro-nightly@latest
```

`vite.config.ts` plugin order: `devtools()`, `tailwindcss()`, `tanstackStart()`, `nitro()`, `viteReact()`.

Nitro auto-detects the `vercel` preset at build time via the `VERCEL` env var that Vercel's build system sets, and emits Build Output API v3 artifacts directly to `.vercel/output/` (confirmed locally: without `VERCEL` set, `pnpm build` falls back to the `node-server` preset and writes `.output/` instead — both are gitignored).

`vercel.json` sets `"framework": null` so Vercel's dashboard doesn't misdetect this as a plain Vite project (which would expect a static `dist/` folder) and instead just runs the configured Build Command and picks up `.vercel/output/`.

Vercel project settings:
- Install Command: `pnpm install` (default)
- Build Command: `pnpm build` (default — runs `vite build`, which is what actually invokes Nitro)
- Output Directory: leave default/empty — Build Output API v3 in `.vercel/output/` takes precedence once present
- Env vars: `CONVEX_DEPLOYMENT`, `VITE_CONVEX_URL` (see above)

Gotcha: if Nitro ever fails to auto-detect Vercel (e.g. a future Nitro version changes detection), set `NITRO_PRESET=vercel` as a Vercel env var to force it.

Verified locally: `pnpm build` completes successfully with the `nitro()` plugin wired in (SSR bundle + client bundle + Nitro server output all built without errors).

## Known gotchas

- `intent install` overwrites `AGENTS.md` wholesale rather than merging — it does NOT just insert the skill-loading block into an existing file. This file was rebuilt from scratch after that ran; if you rerun `intent install`, re-add project-specific content below the skill block afterward.
- Import alias is `#/*` (Node subpath imports), not the more common `@/*` — `components.json` and `tsconfig.json` both point shadcn/imports at `#/*` (a `@/*` alias also exists in `tsconfig.json` as a fallback, but new code should use `#/*` to match what's already there).
- `src/routeTree.gen.ts` and everything under `convex/_generated/` are generated — don't hand-edit; regenerate via `pnpm generate-routes` (routes) or the Convex dev/deploy commands (Convex types).
- Convex demo route (`src/routes/demo/convex.tsx`) sets `ssr: false` — Convex's React client is client-only in this scaffold.
